## Step 2: 有価証券報告書 一覧取得 ✅

**実施日**: 2026-05-13

### 当初方針と修正

EDINET API v2 の書類一覧エンドポイント `/api/v2/documents.json` の制約として、**`date` / `type` / `Subscription-Key` の3パラメータしか受け付けない**ことが公式仕様書（ESE140206 第3-1-1節）で確認できた。EDINETコードや書類種別でのサーバーサイドフィルタは不可能。

そのため、企業の過去報告書を集めるには「日付を変えながらリクエストを繰り返してクライアント側で絞り込む」しかない（日付ループ）。

#### 当初実装
- 過去10年（約2,500営業日）を全部スキャン → 1日1秒sleepでも約42分かかる、APIコール過剰

#### 修正後（窓スキャン方式）
**金融商品取引法 第24条**より、有価証券報告書は事業年度終了後3ヶ月以内に提出義務がある。実際にはほぼ全社が「決算月+3ヶ月目」にまとめて提出する（例: 3月決算 → 6月提出）。

そこで「決算月+3ヶ月目 ± 7日のバッファ」だけをスキャンする方式に変更した。

- 10年・3月決算企業: 約314営業日のみスキャン → 1コール1秒で約5〜6分
- 3年・3月決算企業: 約93営業日 → 約1.5分

### 実装上の注意（バグと修正）

実装の初版は `today.year - year_offset` を起点に窓を計算していたため、今日（2026-05-13）のように当年の提出窓口（6月）に**入る前**だと未来の空窓を含めてしまい、最古年が1年取りこぼされる問題があった。

修正後は **「提出窓が今日時点で終了済みの最新年度」を起点**にして遡る方式に変更。

### インデックスキャッシュ案（本検証では未実施・本実装で要否を再判断）

書類一覧API `/api/v2/documents.json` のレスポンスは「**その日の全企業の書類インデックスだけ**」（XBRL本体は含まない）。1日あたり約430KB / 約460件。

これは「日付さえ決まればレスポンスは不変」（過去日付は変わらない）という性質を持つので、**ローカルにキャッシュしておけば再API不要**になる。

#### 効くシナリオ

| シナリオ | キャッシュの効果 |
|---------|----------------|
| 1社をたまに調べるだけ | **小**（窓スキャン1回で十分・約1.5〜5分） |
| 複数社を横断比較する（業界分析等） | **大**（同じ日付のレスポンスを使い回せる） |
| 訂正報告書や四半期報告書を後から追加で見たい | **大**（同じインデックスから docTypeCode を変えて再抽出可能） |

#### 設計メモ

- 保存先: `data/cache/index/YYYY-MM-DD.json`（生レスポンスをそのまま）
- 取得済み日付の管理: `data/cache/scanned_dates.txt`（再実行時のスキップ判定）
- 10年・全営業日でも合計 約1GB、窓スキャンなら約130MB

#### 判断

本検証フェーズでは**実装しない**。「1社の有報を取れるか」の確認が目的であり、キャッシュなしでも合否確認できる。本実装で「複数社対応」「他書類種別の追加」が決まった時点で導入する。

### 申し送り

- レート制限: 公式仕様書には記載なし。野良情報では3〜5秒間隔推奨。今回は1秒で安定動作したが、本実装では3秒程度に上げる余地あり
- 窓スキャンの前提（決算月+3ヶ月目に提出）は金商法上の義務で担保されているが、訂正報告書（docTypeCode=130）は提出時期がずれる可能性があり、別途検討が必要
- Step 3 では取得した docID から XBRL zip を順次ダウンロードしてパースする

## Step 3a: XBRL パース・主要勘定科目抽出（lxml）

**実施日**: 2026-05-13
**スクリプト**: `step3a_lxml.py`
**対象**: トヨタ自動車 FY2024（period=2024-04-01〜2025-03-31, docID=S100VWVY）
**ライブラリ**: `lxml==5.4.0`

### XBRL 構造の整理

EDINET API の `type` パラメータの仕様取り違えがあり修正済み（書類取得API: `type=1=XBRL zip` / `type=2=PDF`／書類一覧APIとは意味が異なる）。

XBRL データの構造詳細は [edinet_api_overview.md](edinet_api_overview.md) の「XBRL データ構造の要点」セクションを参照。要約:
- **3軸の理解が必要**: 名前空間（タクソノミ）、context（時点・対象）、取得経路（複数経路で同じ値）
- トヨタは **IFRS連結提出**だが、XBRL内に `jppfs_cor`（日本基準・単体）、`jpigp_cor`（IFRS・連結）、`jpcrp_cor`（開示府令）が同居
- 企業固有名前空間 `jpcrp030000-asr_<EDINETコード>-000` は企業ごとに異なるため動的解決が必要

### 2経路の抽出と突合

ユーザー指示により2つの抽出経路を並行で実装し、共通項目で値を突合した。

| 経路 | 名前空間 | 性質 |
|------|---------|------|
| Path A | `jpigp_cor` + 企業固有 | 連結IFRS本体（詳細な財務諸表） |
| Path B | `jpcrp_cor` の `*SummaryOfBusinessResults` | 過去5期分の経営指標サマリ |

### 設計上の発見

1. **`NetAssets` の定義揺れに注意**
   - 当初 Path A で `jpigp_cor:EquityIFRS`（全持分）を選ぶと、Path B の `EquityAttributableToOwnersOfParentIFRSSummaryOfBusinessResults`（親会社株主帰属）と一致しない
   - 差額 = 非支配株主持分
   - 「純資産」の慣用は**親会社株主帰属**側のため、Path A も `jpigp_cor:EquityAttributableToOwnersOfParentIFRS` に揃えた

2. **同じ要素名でも context 指定が必須**
   - `jpigp_cor:OperatingProfitLossIFRS` は1つの XBRL に12回出現（前期・当期 × 各セグメント等）
   - `contextRef="CurrentYearDuration"`（_Memberなし）でフィルタしないと内訳値を拾ってしまう

3. **企業固有名前空間の動的解決**
   - 売上 `SalesRevenuesIFRS` はトヨタの場合 `jpcrp030000-asr_E02144-000` 配下
   - `E02144` はトヨタのEDINETコード。他社では別の URI になる
   - スクリプト内では `ISSUER` というプレースホルダで定義し、実行時に nsmap から動的解決

本実装フェーズでは **AI（Agent Skill）による要素名の動的解決** が有力候補となる。詳細は次のドキュメントにまとめた:

- ホワイトリスト精度を上げる方向では、「全社対応」の壁を越えられない
- LLM による動的解決のほうが拡張性が高く、最終成果物の現実的な形に近い
- Arelle は計算関係チェックには有用だが、要素名の意味判定（本質的な課題）は解決しない

## Step 4: 複数期の時系列 DataFrame 化 ✅

**実施日**: 2026-05-14
**スクリプト**: `step4_timeseries.py`
**対象**: トヨタ自動車（7203）3期分（FY2022〜FY2024）
**ライブラリ**: `pandas==2.3.3`

### 設計

`step3a_lxml.py` の抽出関数群を `import` して再利用する設計とした。step3a を「**1期分の抽出ロジック**」、step4 を「**それを複数期にループして DataFrame 化する薄いラッパー**」と役割分担。

`step3a_lxml.py` には今回 `merge_paths()` 関数を新規追加した。Path A・Path B のどちらに値があるかで自動選択する（Path A 優先・なければ Path B）。これによって step4 は「**最終値の辞書**」だけを受け取って DataFrame の1行にできる。

### 入出力

- 入力: `data/doc_list_{sec_code}.csv`（step2 で生成）
- 出力: `data/timeseries_{sec_code}.csv`

### 検証コマンド・出力

### 検出した非自明な事象: 株式分割の調整基準時点の不一致

ソニーは **2024-10-01 に1株→5株の株式分割**を実施。これが PER/PBR の異常を引き起こした。

直接実機で確認した結果（`step3a --explore` で各報告書のEPS要素を一通り抽出）:

```
Sony FY2022 報告書 (S100QZT6, 提出 2023-06-20, 分割前):
  Prior2YearDuration (=FY2020) = 836.75
  Prior1YearDuration (=FY2021) = 711.84
  CurrentYearDuration (=FY2022) = 758.38

Sony FY2024 報告書 (S100W19Q, 提出 2025-06-20, 分割後):
  Prior4YearDuration (=FY2020) = 167.35   ← 836.75 / 5 ≒ 167.35
  Prior3YearDuration (=FY2021) = 142.37   ← 711.84 / 5 ≒ 142.37
  Prior2YearDuration (=FY2022) = 162.71   ← 758.38 / 5 ≒ 151.68 とは少し異なる
                                                (期中加重平均株式数の再計算による細部差)
  Prior1YearDuration (=FY2023) = 157.66
  CurrentYearDuration (=FY2024) = 188.71
```

→ **EDINETのSummary系EPSは「報告書提出時点の発行済株式数」で計算された値が XBRL に焼き付いている。後の報告書で過去5期を見ると、そのときの株式数（分割後）で再計算済み**。

| データ | 調整基準時点 |
|--------|--------|
| EDINET 各報告書のEPS | **その報告書提出時点**の株式数 |
| yfinance の Close（auto_adjust=False） | **最新分割比率**で遡及調整 |

両方とも「分割調整済み」だが、基準時点が違うため、**「分割が報告書提出より後に起きると整合しなくなる」**。

ソニー FY2022 の PER:
- step4 は FY2022報告書から EPS=758.38 を読む（提出時点では分割前）
- yfinance は 2023-03-31 終値=2,397円 を返す（既に分割後相当に調整済み）
- → PER = 2,397 / 758.38 = **3.16倍**（誤）
- 正しくは 2,397 / 162.71（FY2024 報告書の Prior2 から取得した分割後 EPS）= **14.7倍**

トヨタが問題ないのは、分割が **2021-09-29** と古く、FY2022 報告書（提出 2023-06-30）の時点で**既に分割後**だから。全期間が一貫して分割後値で揃っている。

### 本検証での結論

**EDINETのSummary系 EPS は「報告書提出時点の発行済株式数」を基準に焼き付けられる**。これは XBRL の作りとしては合理的だが、時系列分析には注意が必要:

1. **同じ期の EPS が、どの報告書を読むかで違う値になる**
   - 例: ソニー FY2022 EPS = 758.38（FY2022報告書）/ 162.71（FY2024報告書）
2. **step4 の現実装**は各期の「当該期報告書」から EPS/SharesOutstanding を読むので、分割が起きると不連続になる
3. **本実装での対処**: 「全期を最新報告書のSummary値で揃える」か、「分割比率（yfinance.Ticker.splits）で過去値を割って統一」のいずれか

同様の問題は BPS（純資産÷株式数）にも適用される。

yfinance の auto_adjust について:
- `auto_adjust=True`（デフォルト）: 分割＋配当の完全調整
- `auto_adjust=False`: 「Close」は分割調整のみ、「Adj Close」は配当も含めた調整
- いずれも「最新分割比率での遡及調整済み」（Yahoo Finance側のデータ自体がそうなっている）
- pre-research では `auto_adjust=False` を採用（Closeカラムが明示的な「分割調整済み終値」と分かるため）

### 再現性・ドキュメントの自己点検（Step 5 振り返り）

検証ライブ中に**自分自身の理解が一度誤った**（「EDINETのEPSは未調整」と書いてしまった）ため、コードと verification_results.md を後で訂正した。今後の再現性を担保するため、何が起きてどう直したかを記録する。

**最初の誤解**: 「EDINETのEPSは提出当時のまま固定」「yfinance側だけ分割調整済み」→ 「過去EPSを分割比率で割ればPERが直る」

**実態**: 「**EDINETの `*SummaryOfBusinessResults` EPSは、その報告書提出時点の株式数で再計算済み**」。だから FY2022 報告書（提出 2023-06）の FY2022 EPS と、FY2024 報告書（提出 2025-06）の Prior2YearDuration（=FY2022 EPS）は**別の数値**になる。

**根本原因の検証手順**: 各報告書から `BasicEarningsLossPerShareIFRSSummaryOfBusinessResults` を全 context で抽出して並べる。これで「同じ期の EPS が報告書ごとに変わる」事実が一発で確認できた（上記表）。

**学び（コーディング方針への反映）**:

1. **「要追加調査」と書いて先送りしてはいけない**。XBRLの解釈にまつわる謎は、その場で実機（cached zip）を見れば必ず答えが出る。後で読み返す自分が同じ調査を繰り返す
2. **コードコメントに「自分の仮説」ではなく「実機で確認した事実」を書く**。今回 `fetch_fiscal_year_end_prices` の docstring に「未調整」と書いてしまっていたが、それは仮説で、検証で否定された
3. **データの基準時点（reference point）は必ずdocstring化する**。「分割調整済み」だけでは不十分で「いつの分割比率に揃っているか」までセットで書く必要がある

**訂正後の状態**:
- `step5_metrics.py` の docstring に「EDINET と yfinance で**分割調整の基準時点が違う**」「Sony を具体例とした PER の正誤」を明記
- `step4_timeseries.py` の docstring に「EPS/SharesOutstanding は**当該報告書提出時点の株式数基準**」を追記
- 本ドキュメントの該当節を「実機検証で確認した事実」ベースに書き直し

### 申し送り（Step 6・本実装向け）

- **株式分割の遡及調整（本実装の主要課題）**: 選択肢は2つ
