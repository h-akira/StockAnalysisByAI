# ENH-007: レポート生成層の AI 裁量化（固定スクリプトは元データ取得まで・以降は AI ＋ CWD/scripts）

## ステータス

未着手

## 起票日

2026-05-31

## 種別

仕様追加

## 概要

固定スクリプト（`pipeline.py`）の責務を「**EDINET/yfinance からの元データ取得＋一次指標計算＋一次 JSON 出力**」までに留め、それ以降の「会社固有の加工（株式分割補正等）・雛形外の指標/分析・最終レポートの仕上げ・成果物の妥当性評価」を **AI 裁量**に移す。AI は必要に応じてユーザー CWD の `./scripts/` に**再現可能な加工スクリプト**を新規作成し、一次 JSON を読んで**代替 JSON**を生成、レポートに反映する。一次 JSON は不可侵とし、AI 補正は別ファイルに出す。`./scripts/` には README で記録を残す規律を課す。

> **本 enhancement は設計の根幹（責務分界）に関わる。** [init_plan.md](../init_plan.md) は初期計画の
> 記録であり**不可侵**（書き換えない）。本 enhancement のように init_plan.md の責務分界を上書き・更新する
> 設計判断は、**別ファイルの設計改訂ノート**（ADR 的なドキュメント。`tmp/QA_skill_invocation.md` と同様の
> 設計議論記録の体裁）に記し、init_plan.md のどの節をどう上書きするかを明示する。init_plan.md 本体には
> 手を入れない。本起票は設計提案であり、実装着手は別途レビューと改訂ノートの整備の後とする。

## 背景・動機

manual_test_03（NTT 9432・[review_report.md](../manual_test_03/review_report.md)）で 2 つの構造的弱点が顕在化した:

1. **会社固有の加工を固定ロジックが吸収しきれない（PBR 分割未補正）**: NTT は 2023 年に 1:25 分割を
   実施。PBR = 調整後株価 /（NetAssets / 報告時点 Shares）で分子・分母の基準がずれ、7 期中 5 期の
   PBR が 0.02〜0.07 倍という壊滅的な異常値になった。PER は restated EPS で補正済みなのに PBR だけ
   補正チャネルが無い。こうした「会社ごとに違う加工要件」を固定スクリプトで網羅し続けるのは困難で、
   未対応の間は明白な誤値が成果物に残る。
2. **AI が成果物を仕上げる余地が無い**: [report_template.html.j2](../skills/japan-stock-analysis/templates/report_template.html.j2)
   は「警告＋グラフ＋参照」固定で、投資所見や雛形外の指標を載せる場所が無い。AI 介在型 Skill なのに、
   定性判断・例外対応・最終品質チェックを AI が担えない。

本プロジェクトの設計思想は「会社差・定性判断は AI に委ねる」（[AGENTS.md](../AGENTS.md) §設計思想）。
レポート生成層までこの思想を一貫させ、**固定スクリプトは監査可能な一次計算に徹し、例外対応と仕上げを
AI に委ねる**ハイブリッドにする。ただし AI 生成スクリプトの「使い捨て」による再現性喪失を避けるため、
`./scripts/` への永続化と README 記録を規律として課す。

## 要件

### R1. 責務分界（ハイブリッド）

- **固定スクリプト（`pipeline.py` 系）が担う範囲**: XBRL 取得・要素抽出・timeseries・split_adjust・
  一次指標計算（PER/PBR/ROE 等、現行どおり）・一次 JSON（`data_{code}.json`）出力・warnings。
  ここは引き続き pytest で回帰を担保する**監査済みの土台**。一次計算はベストエフォートで出し続ける
  （不確かな期も値＋warning を出す。例: PBR 分割未補正期）。
- **AI が担う範囲**: 一次 JSON を読んでの妥当性評価／会社固有の加工（分割補正等）／雛形外の指標・
  分析（ユーザー要望）／最終レポートの仕上げ（投資所見含む）／不自然な値が残らないことの確認。

### R2. 一次情報の不可侵と代替 JSON（元データと計算値の明示分離）

- `data_{code}.json`（固定スクリプト生成）は**一次情報として上書き・改変しない**。常に追跡可能に保つ。
- **一次 JSON 内で「元データ」と「計算値」を明示的に区別する**（境界を明確にし、AI がどこを上書きして
  よいかを一意にする）:
  - **元データ（不可侵）**: XBRL から抽出した生の財務数値（現 `financials` の NetSales / OperatingIncome /
    ProfitLoss / EarningsPerShare / TotalAssets / NetAssets / InterestBearingDebt / 各 CF / SharesOutstanding）と、
    yfinance の生株価（現 `metrics.StockPrice`）。これは AI も補正スクリプトも**書き換えてはならない一次値**。
  - **計算値（AI 上書き可）**: 財務値・株価から導出する指標（現 `metrics` の OperatingMargin / NetMargin /
    ROE / EquityRatio / DERatio / SalesGrowth / ProfitGrowth / BPS / EPSForPER / PER / PBR）と、派生量
    （現 `financials.FreeCF` は OperatingCF+InvestingCF の計算値なので「計算値」側に位置づけ直す）。
    これらは固定スクリプトがベストエフォートで出すが、AI が代替 JSON で**再計算・上書きしてよい**。
  - スキーマ上はブロックを分けるか、各値に `source: "xbrl" | "yfinance" | "computed"` 等のタグを付けて
    区別する（詳細は未確定事項で詰める）。`docs/json_schema.md` に反映。
- AI による補正・追加分析は、`./scripts/` のスクリプトが**元データを入力に計算値を再計算**し、**代替 JSON**
  （例 `data_{code}_adjusted.json`）を**全量**生成する（差分のみではなく、レポートが単独で読める完全な JSON）。
  **元データ部分は一次 JSON からそのまま引き継ぎ、計算値部分のみ差し替える**。
- レポート生成は「代替 JSON が存在すればそれを、無ければ一次 JSON を」読む。代替には「どの計算値を
  どう補正したか」「典拠（どの XBRL 要素/コンテキスト/有報）」「一次計算値との対比」をメタ情報として持たせる。
- 雛形外の独自指標（ユーザー要望）も「元データ＋（必要なら他の計算値）から導く計算値」として代替 JSON に
  追加できる。元データは常に不可侵。

### R3. ユーザー CWD の `./scripts/` 規約

- 配置場所は **ユーザーが Skill を起動した CWD**（`.claude/skills/...` ではなく、`report_*.html` /
  `data_*.json` が出るのと同じディレクトリ。例: `manual_test_03/`）の直下 `./scripts/`。
- **ファイル名は銘柄番号で識別、日付は付けない**（例: `9432_pbr_split_adjust.py`）。同一 CWD で複数銘柄を
  扱うため銘柄番号は必須。日付は煩雑なので付けない。雛形外の追加分析も同様（例: `9432_segment_analysis.py`）。
- `./scripts/README.md` を必須とし、各スクリプトについて「対象銘柄／目的／入力（読む JSON）／出力
  （生成する代替 JSON 等）／一次値からの補正内容と根拠」を記録する。再現性・監査性を担保する規律。
- スクリプトは一次 JSON（と必要なら cache/XBRL）を入力に、決定論的に代替 JSON を生成する純粋な処理に
  する（乱数・時刻依存を避け、再実行で同じ結果になること）。

### R4. SKILL.md フロー追加（評価と仕上げの反復ループ）

- 既存 §7（出力の解釈）の後に、新ステップ「**レポートの評価と仕上げ**」を追加する。**所見や補正は HTML の
  後付けではなく、レポート生成スクリプト（CWD/scripts のコピー）に書き込まれ、その実行結果として HTML に
  織り込まれる**。標準ケースは初回出力のまま追記なしで完成し、補正・所見が要る場合だけ「編集 → 再実行」の
  ループを回す（＝「一度 HTML を出してから、必要ならスクリプトを編集して再生成する」反復方式）。
  1. success 後、`assets/` の参考実装を CWD/scripts にコピーして実行し、**まず標準レポート（HTML）を一度
     出力する**。
  2. **出力された HTML と一次 JSON を AI が読んで評価する**: 不自然な値（PBR が極端に小さい/大きい、指標が
     桁外れ、分割をまたぐ系列の不連続等）が無いか、所見を加えるべきか。
  3. 問題が無ければそのまま完成。**補正・所見・雛形外の指標が必要なら、CWD/scripts のコピーを編集**
     （所見セクションの記述、補正計算による代替 JSON 生成、独自指標の追加）し、**再実行して仕上げる**。
     必要に応じてこの評価→編集→再実行を繰り返す。
  4. 編集した場合は `./scripts/README.md` に記録を残す。
  5. **投資所見**（財務トレンド・バリュエーション・リスク）は、完成した HTML を踏まえて一定の自由度で
     記述し、スクリプト経由でレポートに織り込む（断定的な売買推奨は避ける）。
- これらは [AGENTS.md](../AGENTS.md) §設計思想（会社差・定性判断は AI に委ねる、コード固定化に走らない）と
  一貫させる。

### R5. ガードレール（数値の正確性・投資助言の節度）

- AI 生成スクリプトの計算は、可能な限り**典拠（XBRL の実値・有報の遡及列）に基づく**こと。推測値・
  暗算値を代替 JSON に書かない（[ENH-004](004_mapping_rationale_value_cross_check.md) の rationale 規律と同じ精神）。
- 補正の前後で一次値と代替値を対比してユーザーに提示し、何をどう変えたか透明化する。
- 投資所見は**断定的な売買推奨を避け**、事実（数値）と解釈（所見）を区別する。
- レポートテンプレートは「データ品質 warning」「AI 所見」「補正の記録」を**別セクション**にし混ぜない。

### R6. テンプレート拡張

- `report_template.html.j2` に「分析コメント（AI 所見）」セクションと、補正があった場合の「補正の記録」
  セクション（一次値→補正値の対比・根拠・生成スクリプト名）を追加する。render 時に AI が用意した
  内容（Markdown/HTML）を流し込む（例 `{{ analyst_comment | safe }}` / `{{ adjustment_notes | safe }}`）。

### R7. 最終レポートの出力方式（参考実装の CWD コピー方式）

レポート生成は「**参考実装（assets）を CWD にコピーして使う**」方式で扱う（AI が毎回 HTML を手書き
しない／直接実行の固定スクリプトにも完全固定しない、中間）:

- **参考実装の配置を `scripts/` → `assets/` に降格**: html 生成（現 `scripts/html_report.py` ＋
  `templates/report_template.html.j2`）は「**直接実行される固定スクリプト**」ではなく「**コピーされて使われる
  参考雛形**」なので、`skills/japan-stock-analysis/assets/`（Claude Agent Skills 慣習の補助ファイル置き場）に
  移す。これにより `scripts/` は「`${CLAUDE_SKILL_DIR}/scripts/X.py` で**直接実行されるパイプライン専用**」と
  役割が明確になり、「実行用」と「コピー元」の二役混在を解消する。参考実装は pytest で回帰を担保する
  無垢な基準実装として維持。
- **常に CWD/scripts へコピーして実行**: analyze 時、`assets/` の参考実装をユーザー CWD の `./scripts/`
  （例 `./scripts/9432_report.py`）にコピーする。標準ケース（補正不要）はコピーをそのまま実行し、参考実装と
  同一の標準レポートを得る（再現性◎）。
- **例外時はコピーを編集して再実行**: まず標準レポートを一度出力し、その HTML と一次 JSON を評価したうえで、
  会社固有の補正（PBR の分割補正等）・雛形外の図表・ユーザー要望の独自分析・AI 所見が必要なときだけ、
  AI が**コピーを編集 → 再実行**して仕上げる（評価→編集→再実行の反復。詳細フローは R4）。編集後スクリプトは
  `./scripts/` に永続し、
  `./scripts/README.md` に「参考実装からの差分・目的・対象銘柄・入出力」を記録する（R3）。`assets/` の
  参考実装は無垢のまま残るので、いつでも基準実装と差分を比較できる。
- これにより AI は「グラフをゼロから書く」手間を負わず参考実装を出発点にでき、会社固有の仕上げを
  再現可能な形で残せる。代替 JSON（R2）を入力に、CWD のコピー（標準ならそのまま／例外なら編集済み）が
  最終 HTML を生成する。

> 配置の含意: `scripts/` = 直接実行されるパイプライン（`pipeline.py` 等、`${CLAUDE_SKILL_DIR}/scripts/X.py`
> 起動）。`assets/` = コピーされて使われる参考雛形（レポート生成実装・テンプレート）。この区別を
> [SKILL.md](../skills/japan-stock-analysis/SKILL.md) §4 と [AGENTS.md](../AGENTS.md) §スクリプト起動方法に反映する。

## 実現案

### 案1: ハイブリッド ＋ ./scripts/ 永続化 ＋ 代替 JSON（採用方針）

上記 R1〜R6。固定スクリプトは監査済みの一次計算まで、AI が評価・例外加工・仕上げを担い、加工は
`./scripts/`（銘柄番号命名・README 必須）に永続化、出力は一次 JSON を不可侵としつつ全量の代替 JSON。
再現性（pytest が効く土台＋永続スクリプト＋README）と AI 裁量（会社固有加工・所見）を両立。

### 案2: 全面移行（固定スクリプトは生データ取得のみ）— 不採用

指標計算・グラフ・レポートを全て AI が使い捨てスクリプトで生成。最も柔軟だが、(a) 監査済み一次計算が
失われ回帰テストが効かない、(b) 金融数値の正確性リスク、(c) 毎回のトークン/時間コスト、が大きい。
本プロジェクトのリスク許容度に合わないため採らない。

### 案3: 現状維持＋個別バグ対応 — 不採用（後退）

PBR や投資コメントを個別に固定実装し続ける。会社差の網羅は終わらず、AI 介在型の強みを活かせない。

## 未確定事項（実装前にレビューで詰める）

- 元データ/計算値の区別をスキーマでどう表現するか（ブロック分割 か 値ごとの `source` タグ か）。
  あわせて `FreeCF` を `financials` から計算値側へ移す影響（json_schema v1.0 → v1.1 等のバージョン扱い）。
- 代替 JSON のスキーマ詳細（補正メタの形式、一次計算値との対比の持ち方、元データ部の引き継ぎ方）。
- レポートが代替 JSON を優先する条件・複数代替がある場合の扱い。
- `./scripts/` 生成物の gitignore 方針（CWD 側成果物として無視するか、テスト領域のみか）。
- 数値正確性の検証手段（AI 生成スクリプトの出力をどう sanity-check するか。一次値との乖離上限など）。
- 設計改訂ノート（別ファイル）に init_plan.md のどの節を上書きするか・新旧の対応をどう記すか（開発者承認）。
- 原本コピー方式（R7）の細部: コピーの命名（`html_report.py` か `{code}_report.py` か）、原本更新時に
  既存コピーをどう扱うか、`./scripts/` 生成物の gitignore 方針。
