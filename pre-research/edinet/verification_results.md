## Step 2: 有価証券報告書 一覧取得 ✅

**実施日**: 2026-05-13

### 当初方針と修正

EDINET API v2 の書類一覧エンドポイント `/api/v2/documents.json` の制約として、**`date` / `type` / `Subscription-Key` の3パラメータしか受け付けない**ことが公式仕様書（ESE140206 第3-1-1節）で確認できた。EDINETコードや書類種別でのサーバーサイドフィルタは不可能。

そのため、企業の過去報告書を集めるには「日付を変えながらリクエストを繰り返してクライアント側で絞り込む」しかない（日付ループ）。

#### 当初実装
- 過去10年（約2,500営業日）を全部スキャン → 1日1秒sleepでも約42分かかる、APIコール過剰

#### 修正後（窓スキャン方式）
**金融商品取引法 第24条**より、有価証券報告書は事業年度終了後3ヶ月以内に提出義務がある。実際にはほぼ全社が「決算月+3ヶ月目」にまとめて提出する（例: 3月決算 → 6月提出）。

そこで「決算月+3ヶ月目 ± 7日のバッファ」だけをスキャンする方式に変更した。

- 10年・3月決算企業: 約314営業日のみスキャン → 1コール1秒で約5〜6分
- 3年・3月決算企業: 約93営業日 → 約1.5分

### 実装上の注意（バグと修正）

実装の初版は `today.year - year_offset` を起点に窓を計算していたため、今日（2026-05-13）のように当年の提出窓口（6月）に**入る前**だと未来の空窓を含めてしまい、最古年が1年取りこぼされる問題があった。

修正後は **「提出窓が今日時点で終了済みの最新年度」を起点**にして遡る方式に変更。

### API以外の代替手段の検討

「日付ループ以外に手段はないか」も並行調査した。結論は **公式手段は他にない**。

| 手段 | 日付ループ回避 | 無料 | 採否と理由 |
|------|:---:|:---:|----------|
| 公式 EDINET API v2 | ❌ | ✅ | **採用**: 公式・リアルタイム |
| edinet-tools (PyPI) | △ | ✅ | 不採用: 内部で日付ループしているだけのラッパー |
| EDINET DB (商用) | ✅ | ❌ | 不採用: 有料 |
| edinet2dataset (SakanaAI) | ✅ | ✅ | 将来検討: 2014-2025の有報を構築済み。リアルタイム性なし |
| ブラウザUI裏のエンドポイント | ? | ✅ | 不採用: 非公式・リバースエンジニアリング事例なし |

**本実装での方針**:
- 第一選択は公式API＋窓スキャン＋取得済みdocIDのキャッシュ
- 過去分の一括ロードが必要になれば edinet2dataset を補完的に使う

### インデックスキャッシュ案（本検証では未実施・本実装で要否を再判断）

書類一覧API `/api/v2/documents.json` のレスポンスは「**その日の全企業の書類インデックスだけ**」（XBRL本体は含まない）。1日あたり約430KB / 約460件。

これは「日付さえ決まればレスポンスは不変」（過去日付は変わらない）という性質を持つので、**ローカルにキャッシュしておけば再API不要**になる。

#### 効くシナリオ

| シナリオ | キャッシュの効果 |
|---------|----------------|
| 1社をたまに調べるだけ | **小**（窓スキャン1回で十分・約1.5〜5分） |
| 複数社を横断比較する（業界分析等） | **大**（同じ日付のレスポンスを使い回せる） |
| 訂正報告書や四半期報告書を後から追加で見たい | **大**（同じインデックスから docTypeCode を変えて再抽出可能） |

#### 設計メモ

- 保存先: `data/cache/index/YYYY-MM-DD.json`（生レスポンスをそのまま）
- 取得済み日付の管理: `data/cache/scanned_dates.txt`（再実行時のスキップ判定）
- 10年・全営業日でも合計 約1GB、窓スキャンなら約130MB

#### 判断

本検証フェーズでは**実装しない**。「1社の有報を取れるか」の確認が目的であり、キャッシュなしでも合否確認できる。本実装で「複数社対応」「他書類種別の追加」が決まった時点で導入する。

### 申し送り

- レート制限: 公式仕様書には記載なし。野良情報では3〜5秒間隔推奨。今回は1秒で安定動作したが、本実装では3秒程度に上げる余地あり
- 窓スキャンの前提（決算月+3ヶ月目に提出）は金商法上の義務で担保されているが、訂正報告書（docTypeCode=130）は提出時期がずれる可能性があり、別途検討が必要
- Step 3 では取得した docID から XBRL zip を順次ダウンロードしてパースする

## Step 3a: XBRL パース・主要勘定科目抽出（lxml）

**実施日**: 2026-05-13
**スクリプト**: `step3a_lxml.py`
**対象**: トヨタ自動車 FY2024（period=2024-04-01〜2025-03-31, docID=S100VWVY）
**ライブラリ**: `lxml==5.4.0`

### XBRL 構造の整理

EDINET API の `type` パラメータの仕様取り違えがあり修正済み（書類取得API: `type=1=XBRL zip` / `type=2=PDF`／書類一覧APIとは意味が異なる）。

XBRL データの構造詳細は [edinet_api_overview.md](edinet_api_overview.md) の「XBRL データ構造の要点」セクションを参照。要約:
- **3軸の理解が必要**: 名前空間（タクソノミ）、context（時点・対象）、取得経路（複数経路で同じ値）
- トヨタは **IFRS連結提出**だが、XBRL内に `jppfs_cor`（日本基準・単体）、`jpigp_cor`（IFRS・連結）、`jpcrp_cor`（開示府令）が同居
- 企業固有名前空間 `jpcrp030000-asr_<EDINETコード>-000` は企業ごとに異なるため動的解決が必要

### 2経路の抽出と突合

ユーザー指示により2つの抽出経路を並行で実装し、共通項目で値を突合した。

| 経路 | 名前空間 | 性質 |
|------|---------|------|
| Path A | `jpigp_cor` + 企業固有 | 連結IFRS本体（詳細な財務諸表） |
| Path B | `jpcrp_cor` の `*SummaryOfBusinessResults` | 過去5期分の経営指標サマリ |

### 設計上の発見

1. **`NetAssets` の定義揺れに注意**
   - 当初 Path A で `jpigp_cor:EquityIFRS`（全持分）を選ぶと、Path B の `EquityAttributableToOwnersOfParentIFRSSummaryOfBusinessResults`（親会社株主帰属）と一致しない
   - 差額 = 非支配株主持分
   - 「純資産」の慣用は**親会社株主帰属**側のため、Path A も `jpigp_cor:EquityAttributableToOwnersOfParentIFRS` に揃えた

2. **同じ要素名でも context 指定が必須**
   - `jpigp_cor:OperatingProfitLossIFRS` は1つの XBRL に12回出現（前期・当期 × 各セグメント等）
   - `contextRef="CurrentYearDuration"`（_Memberなし）でフィルタしないと内訳値を拾ってしまう

3. **企業固有名前空間の動的解決**
   - 売上 `SalesRevenuesIFRS` はトヨタの場合 `jpcrp030000-asr_E02144-000` 配下
   - `E02144` はトヨタのEDINETコード。他社では別の URI になる
   - スクリプト内では `ISSUER` というプレースホルダで定義し、実行時に nsmap から動的解決

### 本実装方針への示唆

二社検証の結果、**会社による違いは「ホワイトリストで吸収できる小さい違い」と「事前列挙が困難な大きい違い」の2種類**に分かれることが分かった。後者は会計基準・業種・企業独自要素の組み合わせで爆発的に増えるため、ホワイトリスト方式での全社対応は現実的でない。

本実装フェーズでは **AI（Agent Skill）による要素名の動的解決** が有力候補となる。詳細は次のドキュメントにまとめた:

→ **[xbrl_company_variation.md](xbrl_company_variation.md)**：会社間差異の体系的整理＋本実装の選択肢（ホワイトリスト方式／LLM動的解決／ハイブリッド）＋LLMに渡すべきナレッジ

これにより **Step 3b（Arelle補助検証）は当初計画から外す**判断とした。理由:

- ホワイトリスト精度を上げる方向では、「全社対応」の壁を越えられない
- LLM による動的解決のほうが拡張性が高く、最終成果物の現実的な形に近い
- Arelle は計算関係チェックには有用だが、要素名の意味判定（本質的な課題）は解決しない

### 申し送り（Step 3b・本実装向け）

- **CF三表の本体抽出は未実装**: Path A での営業/投資/財務 CF は要素名を特定中に対象スキャンが切れた（Summary経路で値は取れているため pass criterion は満たしているが、再現性のため特定したい）
- **Path A の EPS 抽出も未実装**: `jpigp_cor` に直接の EPS はなく、`NotesEarningsPerShare...TextBlock` 等の文書要素しかない模様。本体IFRSステートメントは構造化されておらず Summary 経由が現実的
- **本実装での要素ホワイトリスト**: 今回特定した要素名は IFRS提出企業の前提。日本基準提出企業では `jppfs_cor` 系がメインになる（フォールバック候補は既にコード内に書いてある）。3社目以降の検証は本実装フェーズで業種を変えて行う
